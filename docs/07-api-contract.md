# API-контракт

Сервер для v2 будет переработан. При этом приложение должно уметь полностью работать без сервера для малых соревнований. Документ фиксирует требования к новому API и отдельно описывает старый API для миграции.

## Принципы нового API

| Принцип | Требование |
|---|---|
| Идемпотентность | Повторная отправка не должна создавать дубли |
| Версионирование | Новый контракт должен иметь явную версию |
| Offline sync | Клиент может отправлять накопленные события после восстановления связи |
| Справочники | Классы и корты могут приходить с сервера; игроки и команды являются опциональными метаданными |
| Автономная работа | Клиент может вести матч без серверных справочников игроков |
| Ошибки | Ошибки возвращаются структурировано |

## Сервер как опция

Сервер не должен быть обязательным условием запуска соревнования.

Режимы работы:

| Режим | Описание |
|---|---|
| Автономный | Сервер не настроен, матч ведется по классу и цветам сторон |
| Online | Справочники и матчи синхронизируются с сервером |
| Mixed | Матч ведется локально, сервер используется для поздней синхронизации |

Новый API нужен для больших соревнований и централизованного хранения, но не должен блокировать автономный сценарий.

## Сетевые параметры

Старый счетчик использовал порт `2007`. Для совместимости порт можно оставить, но контракт должен быть новым и явно версионированным.

Пример base URL: `http://localhost:2007/api/v2`.

## Проверка сервера

```http
GET /api/v2/health
```

Ответ:

```json
{
  "status": "ok",
  "serverTime": "2026-05-23T12:00:00.000Z",
  "apiVersion": "2.0.0"
}
```

## Справочники

```http
GET /api/v2/dictionaries
```

Ответ содержит:

| Поле | Назначение |
|---|---|
| `gameClasses` | Классы и времена |
| `participants` | Опциональные участники/игроки для больших соревнований |
| `courts` | Корты |
| `regions` | Регионы |
| `teams` | Команды |
| `countries` | Страны |
| `version` | Версия справочников |
| `generatedAt` | Время формирования |

Клиент сохраняет ответ локально. Offline-mode не требует участников: если серверных участников нет, матч все равно можно вести по классу и цветам.

## Создание или старт матча

```http
POST /api/v2/matches/start
```

Payload должен содержать `clientMatchId`, чтобы сервер мог безопасно обработать повторную отправку.

```json
{
  "clientMatchId": "local-uuid",
  "courtId": null,
  "gameClassId": "bc1m",
  "redSide": { "color": "red", "label": "Красные" },
  "blueSide": { "color": "blue", "label": "Синие" },
  "officials": null,
  "startedAt": "2026-05-23T12:00:00.000Z"
}
```

## Отправка энда

```http
POST /api/v2/matches/{clientMatchId}/ends/{endIndex}
```

```json
{
  "clientEventId": "event-uuid",
  "end": {
    "index": 1,
    "redScore": 1,
    "blueScore": 0,
    "redTimeUsedSec": 145,
    "blueTimeUsedSec": 183,
    "completedAt": "2026-05-23T12:10:00.000Z"
  }
}
```

## Завершение матча

```http
POST /api/v2/matches/{clientMatchId}/finish
```

В автономном режиме завершение матча не требует кода/пароля. В серверном режиме сервер может требовать код/пароль для финальной отправки. Пароль не должен быть hardcoded в renderer.

```json
{
  "clientEventId": "event-uuid",
  "finishCode": "******",
  "match": {},
  "actionLog": [],
  "completedAt": "2026-05-23T13:00:00.000Z"
}
```

## Журнал действий

Сервер должен принимать журнал действий вместе с матчем или отдельным endpoint.

```http
POST /api/v2/matches/{clientMatchId}/action-log
```

Журнал нужен для спорных ситуаций и восстановления.

## Ошибки

Ошибки должны быть машинно-читаемыми.

```json
{
  "error": {
    "code": "MATCH_ALREADY_FINISHED",
    "message": "Матч уже завершен",
    "details": {}
  }
}
```

## Offline sync

Если сервер недоступен, клиент не блокирует ведение матча. Он сохраняет задачи в очередь.

При восстановлении связи клиент отправляет задачи с теми же `clientMatchId` и `clientEventId`.

Сервер должен отвечать одинаково на повторные запросы с одинаковыми идентификаторами.

## Старый API

Старый проект использует endpoints:

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/check` | Проверка сервера, ответ `checked` |
| `GET` | `/players` | Список игроков |
| `POST` | `/startMatch` | Начать матч |
| `POST` | `/sendEnd` | Отправить энд |
| `POST` | `/sendMatch` | Отправить матч |

Если нужно временно поддержать старый сервер, в v2 следует сделать adapter-слой, а не смешивать старый контракт с новым доменным кодом.
