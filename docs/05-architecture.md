# Архитектура

## Общая схема

Приложение состоит из Electron main process, preload-слоя, окна оператора, окна табло, локального хранилища и API-клиента.

```text
Electron main
  |-- создает окно оператора
  |-- создает окно табло
  |-- управляет IPC
  |-- управляет локальным storage через безопасные handlers

Preload
  |-- открывает строго ограниченный API для renderer
  |-- скрывает ipcRenderer

Renderer operator
  |-- Vue 3 UI
  |-- Pinia stores
  |-- управление матчем

Renderer scoreboard
  |-- Vue 3 UI табло
  |-- read-only представление состояния матча

Local storage
  |-- настройки
  |-- кэш справочников
  |-- текущий матч
  |-- очередь синхронизации
  |-- журнал действий
  |-- история завершенных матчей SQLite

Server API, опционально
  |-- база игроков
  |-- справочники
  |-- матчи
  |-- синхронизация

Standalone mode
  |-- локальные настройки классов и времен
  |-- один активный матч по классу и цветам
  |-- история завершенных матчей SQLite
  |-- поздняя синхронизация, если сервер появится
```

## Процессы Electron

| Процесс | Ответственность |
|---|---|
| Main | Окна, IPC, файловая система, политика безопасности |
| Preload | Безопасный bridge между renderer и main |
| Operator renderer | Операторский интерфейс |
| Scoreboard renderer | Табло второго окна |

## Окно оператора

Окно оператора является единственным местом, где можно менять матч.

Оператор может выбирать матч, запускать таймеры, менять счет, отправлять энд, завершать матч, открывать настройки.

## Окно табло

Окно табло является read-only.

Табло получает снимки состояния матча через типизированный IPC и не отправляет команд управления матчем.

## Источник истины

Источник истины для активного матча находится в operator renderer store и немедленно сохраняется в локальное хранилище через main process.

Табло получает производный `ScoreboardState`.

Сервер не является источником истины во время активного offline-матча. Сервер получает результат через синхронизацию.

## Локальное хранилище

Локальное хранилище должно содержать:

| Данные | Назначение |
|---|---|
| `settings` | Настройки приложения |
| `dictionaries` | Классы, времена, корты и опциональные серверные справочники |
| `activeMatch` | Текущее состояние матча; восстановление незавершенного автономного матча не обязательно |
| `syncQueue` | Очередь отправки на сервер |
| `actionLog` | Журнал действий оператора |
| `matchHistory` | Завершенные матчи в SQLite |

Формат хранения завершенных матчей: SQLite. JSON допустим только для простых настроек.

## IPC

IPC должен быть типизированным и разделенным по назначению.

Примеры каналов:

| Канал | Направление | Назначение |
|---|---|---|
| `app:getVersion` | renderer -> main | Версия приложения |
| `settings:load` | renderer -> main | Загрузка настроек |
| `settings:save` | renderer -> main | Сохранение настроек |
| `match:saveSnapshot` | operator -> main | Автосохранение матча |
| `scoreboard:update` | main/operator -> scoreboard | Обновление табло |
| `sync:enqueue` | operator -> main | Добавить задачу синхронизации |
| `sync:run` | operator -> main | Запустить отправку очереди |

Запрещено использовать один общий канал для всех сообщений.

## Поток запуска

1. Main process стартует Electron.
2. Main process загружает настройки.
3. Main process создает окно оператора.
4. Main process создает окно табло.
5. Operator renderer загружает локальные справочники.
6. API client проверяет сервер, если сервер настроен.
7. Если сервер доступен, запускается синхронизация справочников.
8. Если сервер не настроен, приложение работает в автономном режиме.
9. Восстановление незавершенного автономного матча после перезапуска не является обязательным требованием.

## Поток матча

1. Оператор выбирает класс матча; в серверном режиме может выбрать матч из расписания и участников.
2. Store создает `MatchState`.
3. Снимок сохраняется локально.
4. Табло получает первый `ScoreboardState`.
5. На каждом изменении времени, счета, энда или статуса создается новый снимок.
6. Снимок сохраняется локально и отправляется на табло.
7. При отправке энда создается задача синхронизации.
8. При завершении матча создается финальная задача синхронизации.

## Offline-mode

Offline-mode не требует базы игроков. Минимально он использует локальные настройки классов и времен.

Если серверные справочники отсутствуют, автономный матч все равно можно создать по классу. Игроки, регионы и команды являются опциональными метаданными и не блокируют ведение счета.

Если матч создан offline, все server actions складываются в `syncQueue`.

## Сервер

Сервер будет переработан, но он не является обязательным для работы приложения. Старые endpoints используются только как описание текущей интеграции и источник миграционных требований.

Новый API должен поддерживать справочники, матчи, идемпотентную синхронизацию и статусы отправки.

## Автономный режим без сервера

Автономный режим является обязательным режимом работы, а не аварийным fallback.

В этом режиме:

| Область | Поведение |
|---|---|
| Сервер | Не требуется |
| Справочники | Минимально нужны классы и времена; игроки не обязательны |
| Игроки | Не выбираются в автономном матче |
| Корт | Не обязателен для старта автономного матча |
| Судьи | Не нужны в автономном матче |
| Этап | Не нужен в автономном матче |
| Матчи | Создаются, ведутся и завершаются локально |
| Активный матч | Один матч за раз |
| Незавершенный матч | Восстановление после перезапуска не обязательно |
| Синхронизация | Не обязательна; доступна позже, если сервер появится |
| Логи | Пишутся локально |
